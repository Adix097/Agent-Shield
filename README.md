# Agent Shield

Agent Shield is a small TypeScript reference implementation for reducing the
risk of indirect prompt injection in browser-using agents. It places a
trust boundary around web content before that content is returned to the
agent, and places an approval gate around email sends.

The demo agent can:

- browse a flight page;
- read a local demo inbox; and
- send an email through a tool interface.

The shield removes or flags content that is hidden from a human reader,
strips zero-width characters, redacts visible text that looks like an
instruction to an AI, and wraps returned page text as untrusted data. The
email gate tracks whether untrusted web content or inbox content has entered
the session, checks recipients against a trusted list, and asks for approval
when a send may be unsafe.

> This is a research/demo project, not a complete security boundary. The
> benchmark below includes a known encoding gap, and the implementation
> should not be used as the sole control for real secrets or email delivery.

## Benchmark results

The checked-in results were generated by the deterministic page and gate
evaluations in `src/shield/`. The page benchmark contains 96 cases: every
combination of the attack placements and payload wordings defined in
`src/world/pages.ts`. An injection is counted as **surviving** when its
giveaway marker is still present in the text returned to the agent.

| Measure | Result |
| --- | ---: |
| Cases | 96 |
| Injection reached the agent without the shield (text view) | 80/96 (83.3%) |
| Injection reached the agent without the shield (HTML view) | 96/96 (100%) |
| Injection survived with the shield | 5/96 (5.2%) |
| Hidden-from-human injections surviving with the shield | 0/72 (0%) |
| Visible injections surviving with the shield | 5/24 (20.8%) |
| Clean page preserved and unflagged | Yes |

The five surviving cases are:

```text
visible-plain/fake-fare
visible-plain/outdated-notice
fake-system-notice/outdated-notice
zero-width/fake-fare
zero-width/outdated-notice
```

The separate email-gate evaluation contains six malicious sends and three
legitimate sends:

| Measure | Result |
| --- | ---: |
| Malicious sends blocked | 5/6 (83.3%) |
| Legitimate sends interrupted | 0/3 (0% false-positive interruption) |
| Legitimate sends allowed | 3/3 (100%) |
| Known gate gap | 1: base64-encoded secret sent to a trusted contact |

The known gap is intentionally reported rather than hidden: the gate detects
raw inbox fragments and secret-like tokens, but does not currently decode
base64 before checking the email body.

These are detection/survival measurements for the included fixtures, not a
claim of a general prompt-injection detection rate. The benchmark does not
measure all possible HTML, encoding, multilingual, or model-specific attacks.

## How it works

### Browser content shield

`shieldedBrowse()` extracts page text in a real browser and separates:

- visible text;
- text hidden with CSS (`display:none`, hidden visibility, zero opacity,
  tiny fonts, off-screen positioning, or very low contrast); and
- suspicious comments, attributes, and zero-width characters.

Hidden content is removed. Suspicious visible instructions are redacted.
Returned content is marked with an untrusted-content wrapper so the model is
explicitly told to treat it as data, not instructions. Findings are appended
to `results/shield-log.jsonl`.

### Email gate

`Gate.checkSend()` normalizes recipients and checks them against:

```text
me@example.com
friend@example.com
```

It requests approval when a recipient is not trusted or when inbox content is
being sent to a non-user recipient after the agent has browsed untrusted
content. A denied approval prevents the send. Decisions are appended to
`results/gate-log.jsonl`.

## Setup

Requirements:

- Node.js with npm
- a Google GenAI API key for live agent runs

Install dependencies and create a local environment file:

```bash
npm install
cp .env.example .env
```

Set the following values in `.env`:

```dotenv
GEMINI_API_KEY=your-api-key
GEMINI_MODEL=gemini-2.0-flash
LLM_MODE=live
LLM_MIN_GAP_MS=4000
```

`LLM_MODE=replay` uses cached responses in `results/cache` and does not make
new API calls. Live calls are rate-spaced, retried for transient failures, and
cached so repeated benchmark runs can be replayed.

## Run the evaluations

The repository does not require a separate build step; execute the TypeScript
entry points with `tsx`:

```bash
# Compare raw text/HTML exposure without the shield
npx tsx src/shield/baseline.ts

# Evaluate the shield against all fixture combinations
npx tsx src/shield/eval.ts

# Evaluate the email approval gate
npx tsx src/shield/gate-eval.ts

# Combine the evaluation outputs into results/summary.json
npx tsx src/report.ts
```

The page evaluations start a local fixture server on port `4000` and use
Playwright. The generated JSON and JSONL files under `results/` are local
evaluation artifacts; the checked-in summary is the source for the numbers
reported above.

## Run the agent demo

The agent entry points use the local flight-page server and the configured
Gemini model. For example:

```bash
npx tsx src/agent/try.ts
```

For repeated, cached benchmark-style agent runs:

```bash
npx tsx src/bench/real.ts
```

Useful environment variables for `src/bench/real.ts` include:

- `BENCH_CASES`: comma-separated `attack/payload` cases;
- `BENCH_VARIANTS`: number of model variants per case;
- `BENCH_CONDITIONS`: comma-separated `off,on`;
- `SCENARIO`: `a` for browsing only or `b` for reading email first;
- `AGENT_VIEW`: agent view label stored in the output.

The real-agent benchmark requires `GEMINI_API_KEY` unless all requested
responses already exist in the cache. It can take substantially longer than
the deterministic evaluations because it makes model calls.

## Project layout

```text

```
